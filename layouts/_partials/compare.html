No claims about other projects. */ -}} {{- $d := hugo.Data.libraries }} {{- $modules := 0 }}{{ $adapters := 0 }} {{- range $d.libraries }}{{ $f := index hugo.Data.facts .name }}{{ $modules = add $modules (len $f.modules) }}{{ $adapters = add $adapters (len $f.contrib) }}{{ end }}

✓ubgo is

  • Separate Go modules. {{ $modules }} go.mod files across the {{ len $d.libraries }} public libraries. You add the ones you use. See the map
  • Small cores, adapters outside them. {{ $adapters }} adapter modules live in contrib/ folders, so an integration's dependencies stay out of your build until you import it. For example errx, logger and health.
  • Backends you can swap, checked by one suite. {{ $withSuite := slice }}{{ range $d.libraries }}{{ if .suite }}{{ $withSuite = $withSuite | append . }}{{ end }}{{ end }}{{ range $i, $l := $withSuite }}{{ if $i }}, {{ end }}{{ $l.name }} ({{ $l.suite.name }}){{ end }}: a backend counts only when its tests run the suite.
  • Fits the HTTP stack you already use. health, shutdown and buildinfo ship adapters for net/http, Gin, Chi, Echo and Fiber.

✕ubgo is not

  • A web framework. There is no ubgo router or request lifecycle. You keep your own, and the libraries plug into it.
  • An ORM. sqlb builds typed SQL; entkit and entx extend the ent ORM instead of replacing it.
  • All or nothing. A library needs another one only when its go.mod says so, and the map draws every one of those links.
